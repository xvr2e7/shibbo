How it works

Three commands between you and a faster database.

Tern never sits in the path of your queries. It reads the statistics your database already keeps and turns them into an opinion.

01

Point it at a database

Connect over the normal protocol, read-only. Tern samples pg_stat_statements, MySQL's performance schema, or the slow log — credentials never leave the process.

$ tern watch postgres://prod-main
connected · sampling 12.5M statements/day
02

Let it read the water

Every statement gets fingerprinted — literals, IN-lists and aliases normalized — then weighed by total impact. A 40 ms query called 40,000 times outranks a one-off 4 second straggler.

$ tern scan --since 24h --top 10
214 fingerprints from 12,584,391 statements
03

Get a report, not a dashboard

Ranked fingerprints, the expensive step of each plan, and an index you can paste. Pipe it, diff it against yesterday, fail CI on it.

$ tern report --format md > findings.md
exit 1 · threshold exceeded · 6.4h recoverable

Features

Built by people who get paged.

Everything a slow-query tool needs, nothing it doesn't. Each row is a decision, not a feature checkbox.

01

Impact ranking, not raw p95

Sorted by calls × latency — the seconds your database actually loses. The view that matches what users feel.

calls × latency
02

Fingerprints that survive real code

10,000 variants of the same query collapse into one signature. Constants, IN-lists, comments and aliases normalized away.

214 fingerprints / 12.5M stmts
03

EXPLAIN on tap

tern explain orders:by-customer pulls the live plan and marks the step eating your time.

plan analysis
04

Fails like a test

--fail-over 500ms exits non-zero when a fingerprint regresses, so CI, cron and your pager can do the waking up.

cron · CI · pagers
05

Never in the path

Passive sampling of existing statistics. Your queries never route through tern, and nothing is written back.

read-only
06

One static binary

Linux, macOS, FreeBSD. No runtime, no daemon, no config file required — copy it over and run.

4.1 MB · go build

The report

Something you can paste into a ticket.

Plain text, ranked by recoverable time, with a suggested fix per offender. Diff it, comment on it, close it.

TERN REPORT  prod-main · postgres 16.2
window 24h · 12,584,391 statements · 214 fingerprints#1  orders:by-customer   46.2% of db time
    p95 4,212 ms · 138 calls · regression ↑
    SELECT * FROM orders WHERE customer_id = $1 …
    cause  seq scan on orders — 1.2M rows, filter hits 0.1%
    fix    CREATE INDEX CONCURRENTLY ON orders (customer_id, created_at DESC);
    saves  est. 3.1 h / day

#2  events:count-range   21.8% of db time
    p95 1,983 ms · 402 calls · stable
    SELECT count(*) FROM events WHERE created_at BETWEEN $1 AND $2
    cause  counting 38M rows with no covering index
    fix    CREATE INDEX ON events USING brin (created_at);
    saves  est. 1.4 h / day

#3  sessions:expire-sweep   9.4% of db time
    p95 712 ms · 1,204 calls · new
    UPDATE sessions SET expires_at = now() + interval '30 days' …
    cause  row-lock contention with the login path
    fix    index (user_id, expires_at); batch the sweep
    saves  est. 0.6 h / day

Install

One command, then forget it's installed.

Tern is a single binary with zero runtime dependencies. Pick your channel.

macOS · Linuxcurl -fsSL tern.sh/install.sh | sh
Homebrewbrew install ternio/tap/tern
Dockerdocker run --rm ternio/tern scan postgres://prod-main

Works with PostgreSQL 12+, MySQL 5.7+ and SQLite. Static binary for linux / darwin / freebsd — amd64 & arm64.
