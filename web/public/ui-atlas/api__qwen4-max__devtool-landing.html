// features

Everything you'd dig through pg_stat_statements for. Nothing you wouldn't.

Tern lives in your terminal, reads what your database already knows, and gets out of the way.

Σ

Ranks by real cost

A 4 ms query called 90,000 times a minute beats a 2-second cron job. Tern sorts by calls × mean, so you fix what actually hurts.

⌁

Live tail mode

tern watch streams queries as they happen, normalized and grouped. Like tail -f, but for your query load.

⌘

Index suggestions

Reads the EXPLAIN plan, spots the seq scans, and prints a ready-to-run CREATE INDEX CONCURRENTLY. You decide whether to ship it.

◫

Zero infrastructure

One static binary. No agent, no sidecar, no SaaS account. Point it at a connection string and it works — even against a read replica.

⇄

Diff two windows

tern diff before.json after.json shows exactly which queries regressed after that deploy. Great in CI, better at 2 a.m.

¶

Scriptable output

Pretty tables for humans, --json for machines. Pipe into jq, post to Slack, fail the build when p95 crosses a threshold.

// how it works

Three commands. One fewer incident.

01 point

Give it a connection string

Reads from your existing stats views. Read-only, never writes, safe on production replicas.

$ tern watch \ --db postgres://replica/app
02 watch

Let traffic tell the story

Tern normalizes literals, groups query shapes, and accumulates calls, mean, p95, and rows examined.

watching… 14 shapes ▲ orders_by_email p95 1.9s seq scan on orders (2.1M rows)
03 fix

Apply the suggestion

One command prints the plan analysis and the index DDL. Re-run and watch p95 fall off a cliff.

$ tern fix orders_by_email CREATE INDEX CONCURRENTLY idx_orders_email ON orders(email); ✓ estimated 214× faster
// sample output
