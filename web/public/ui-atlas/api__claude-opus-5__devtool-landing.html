Why Tern

An APM tells you something is slow.
Tern tells you what to do about it.

Built for the 20 minutes before the on-call page turns into an incident — and for the pull request that would have caused it.

Zero configuration

Point it at a connection string. Tern finds pg_stat_statements, the slow query log, or performance_schema on its own.

Ranked by real impact

Not just the slowest query — the one burning the most total database time. Calls × latency, weighted by lock contention.

Plans in plain English

EXPLAIN ANALYZE output decoded into a sentence a human can read, with the exact node that blew up the estimate highlighted.

Fixes you can paste

Index DDL, rewrites, and batching suggestions — each with a cost estimate and a predicted p95, so you know before you ship.

Guards your CI

tern ci diffs against a baseline and fails the build when a PR introduces a sequential scan or an N+1. Comments on the diff.

Nothing leaves the box

A single static binary. Query text is normalized locally, literals are stripped, and there is no telemetry. Air-gap friendly.

How it works

Three commands, start to fixed.

1

Connect

Read-only credentials are enough. Tern collects statistics, never rows — tern scan --db $DATABASE_URL.

2

Diagnose

Each offender is replayed behind EXPLAIN (ANALYZE, BUFFERS) in a transaction that always rolls back.

3

Fix & watch

Apply suggestions with tern fix, then wire tern ci into your pipeline so it never regresses.

.github/workflows/tern.yml
# fail the PR if a query regresses
name: tern
on: [pull_request]

jobs:
  query-budget:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: tern-dev/setup-tern@v1
      - run: |
          tern ci \
            --baseline .tern/baseline.json \
            --budget p95=150ms \
            --fail-on seqscan,n+1 \
            --comment
