\n

Built for the command line

\n

No dashboards. No agents. Just a fast binary that reads your database and tells you what's wrong.

\n
\n
\n
\n \n
\n

Automatic Query Discovery

\n

Reads from pg_stat_statements, slow query logs, or performance_schema. No code changes required.

\n
\n
\n
\n \n
\n

EXPLAIN ANALYZE

\n

Runs EXPLAIN on flagged queries and surfaces sequential scans, bad join strategies, and missing indexes.

\n
\n
\n
\n \n
\n

Fix Generation

\n

Run tern fix to get ready-to-run CREATE INDEX statements and migration files for your framework.

\n
\n
\n
\n \n
\n

Read-Only by Default

\n

Tern never writes to your database. Scan mode uses only SELECT on system catalogs. Fixes are always dry-run first.

\n
\n
\n
\n \n
\n

CI Integration

\n

Run tern scan --ci in your pipeline. Fails the build when query performance regresses past thresholds you set.

\n
\n
\n
\n \n
\n

Trend Tracking

\n

Run scans on a schedule and Tern tracks latency over time. Catch regressions the week they ship, not the month.

\n

\n\n\n
\n

Three commands. That's it.

\n
\n
\n
1
\n
\n

Connect

\n

Point Tern at your database with a connection string. It auto-detects the engine, version, and available stats extensions. Nothing to install on the server.

\n
\n
\n
\n
2
\n
\n

Scan

\n

tern scan pulls query statistics, runs EXPLAIN on outliers, and ranks every problem by real-world impact: latency × call frequency.

\n
\n
\n
\n
3
\n
\n

Fix

\n

tern fix generates index definitions and rewrites. Review the migration, apply it, and rescan to verify the improvement.
