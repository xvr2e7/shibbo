How it works

From install to answer in under a minute

Tern reads what your database already tracks. It never writes, never proxies, and never phones home.

01

Install the binary

One static binary for macOS, Linux and Windows. No agent to deploy, no sidecar to babysit, nothing new in your stack.

02

Point it at your database

Tern tails pg_stat_statements and slow query logs with read-only credentials that never leave your machine.

03

Ship the fix

Every offender comes with the exact CREATE INDEX and the latency win it buys. Apply it with one flag.

Why Tern

Built for the 2 a.m. page

Most tools show you that something is slow. Tern shows you which query, why it's slow, and the exact fix — ranked by the damage it does.

Ranked by real cost

Tern sorts by total time burned, not average latency — so the 12 ms query called 58,000×/min floats straight to the top where it belongs.

Zero-config adapters

Reads pg_stat_statements, MySQL & MariaDB slow logs, SQLite traces, SQL Server DMVs and Redis SLOWLOG. Point it at the DB and go.

Fixes, not just findings

Every offender ships with the exact CREATE INDEX statement and an estimated latency win — apply it directly from the CLI.

Live watch mode

A terminal dashboard that flags slow queries the second they appear — with the HTTP route, user and deploy attached to each one.

CI performance gate

tern check diffs every PR against your base branch and fails the build when p95 regresses — with a comment naming the culprit query.

One 9 MB binary

Static, dependency-free, runs anywhere — your laptop, a bastion host, a Docker container or a CI runner. Works on macOS, Linux and Windows.

.github/workflows/query-perf.yml 
name: query-perf
on: [pull_request]

jobs:
  tern:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }   # diff against your base branch

      - run: curl -fsSL https://tern.sh/install.sh | sh
      - run: tern check --db "$DATABASE_URL" \
          --baseline origin/main \
          --max-p95 250ms \
          --comment-on-pr
CI gate

Fail the build before your users do

Every pull request gets a query-performance diff. If p95 regresses or a brand-new slow query appears, the check fails and tells everyone exactly which line of SQL did it.

  • Baseline diffing against any branch or tag
  • --max-p95 --max-total hard gates
  • PR comments with the offending SQL and suggested index
  • Works in GitHub Actions, GitLab CI, Buildkite and Buildkite… anywhere
$ tern check --max-p95 250ms ✗ p95 regressed 212ms → 481ms on POST /api/checkout offender: SELECT … FROM carts WHERE user_id = $1 (new in PR #482) ✗ 1 query over budget — failing build
