How it works

Three commands from "it feels slow" to a fix.

Tern reads your database's own statistics and query logs. Nothing to install on the server, nothing to proxy your traffic through.

01 / connect

Point it at a database

Pass a connection string, or let Tern pick it up from your DATABASE_URL. Read-only credentials are all it needs.

$ tern connect postgres://ro@db:5432/shop
✓ connected · pg 16.3 · pg_stat_statements on
02 / watch

Watch it rank the offenders

Queries are normalized, grouped, and sorted by total time burned, not just worst single run. Live, in your terminal.

$ tern watch --since 1h
tracking 1,204 distinct queries…
03 / explain

Get a fix, not a plan dump

Tern runs EXPLAIN ANALYZE, reads the plan for you, and proposes the index, rewrite, or parameter change that helps.

$ tern explain q_8f21
→ seq scan on orders (2.1M rows)
→ suggest: CREATE INDEX …

Features

Built for the person who gets paged.

Everything you need to go from an alert to a merged PR, without opening a browser tab.

Ranked by real cost

A 3 ms query called 40,000 times beats a 2 s query called once. Tern sorts by total time, calls, and p99 so you fix what matters.

Plans, explained

Sequential scans, nested-loop blowups, missing indexes, stale stats. Tern names the problem in plain language and points at the line.

Read-only by default

Tern never writes to your database. Suggested indexes are printed as SQL for you to review, test, and ship through your normal migrations.

Finds it in your code

Give Tern a repo and it maps each slow query back to the ORM call or SQL file that produced it, with file and line number.

Diff two time windows

tern diff compares before and after a deploy and shows exactly which queries got slower, faster, or appeared for the first time.

Scriptable output

Every command takes --json. Pipe it into jq, post it to Slack, or fail a CI job when p99 crosses a threshold.

tern explain

Stop squinting at EXPLAIN output.

Tern reads the plan so you don't have to. It highlights the node that's eating the time, tells you why, and writes the fix.

  • Row estimate mismatches — flags when the planner guessed 10 rows and got 2 million.
  • Index suggestions that fit — column order, partial predicates, and covering indexes, not just "add an index."
  • Safe to run in prod — uses EXPLAIN (ANALYZE, BUFFERS) inside a rolled-back transaction, with a timeout.
  • Before / after — tern explain --try simulates the index with HypoPG and shows the new plan.
tern explain q_8f21plan.json
-- q_8f21 · 4,812 calls/h · total 41.2s · p99 212ms
SELECT o.id, o.total, c.email
FROM orders o JOIN customers c ON c.id = o.customer_id
WHERE o.status = 'pending' AND o.created_at > $1
ORDER BY o.created_at DESC LIMIT 50;

── plan ─────────────────────────────────────────────
Seq Scan on orders  (rows=2,104,331 · 188ms · 94% of time)
  Filter: status = 'pending' AND created_at > $1
  Rows Removed by Filter: 2,097,902
  Nested Loop → Index Scan customers_pkey  (6ms)

── why ──────────────────────────────────────────────
Only 0.3% of rows match, but there is no index covering
(status, created_at). Postgres scans the whole table.

── fix ──────────────────────────────────────────────
CREATE INDEX CONCURRENTLY orders_pending_created_idx
  ON orders (created_at DESC) WHERE status = 'pending';
est. 188ms → 0.4ms · index size ~1.1 MB · tern explain --try

Continuous integration

Catch the regression before it ships.

Run Tern against your test or staging database in CI. It fails the build when a query's p99 crosses your budget, and leaves a comment on the PR showing which one.

GitHub Action docs
# .github/workflows/queries.yml
- uses: tern-db/action@v1
  with:
    database-url: ${{ secrets.STAGING_DB }}
    budget-p99: 50ms
    compare-to: main
    comment: true

# ✗ 1 query exceeded budget
#   q_8f21  p99 212ms (+174ms vs main)
#   app/orders/repo.py:48

Install

One binary. Thirty seconds.

macOS, Linux, and Windows. No runtime, no daemon, no account.

$ brew install tern
$ curl -fsSL https://tern.sh/install | sh
$ cargo install tern-cli
$ docker run --rm -it ghcr.io/tern-db/tern watch $DATABASE_URL

Then run tern watch in any directory with a DATABASE_URL. Postgres needs pg_stat_statements; Tern tells you if it's off.
