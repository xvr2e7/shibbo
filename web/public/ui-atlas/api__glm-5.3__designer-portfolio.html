02

How I work

PRINCIPLES, NOT PROCESS THEATRE

Every project starts with a written problem statement and one number we agree to be judged by. If we can't describe "better" in a single sentence, the pixels aren't ready.

I build the ugliest possible version of the scariest assumption first — a rough Figma file, a coded spike, sometimes a printout taped to a phone. Cheap wrong answers are how expensive ones get avoided.

Screens rot; systems compound. I ship tokens, components and documentation alongside the product, so the two-hundredth screen is as considered as the first.

Handoff is a midpoint, not a finish line. Instrumentation plans, dashboards we actually read, and iteration windows booked before launch — not after the retro.

03

About

AMSTERDAM · 10 YEARS IN · CET
FIG. — THE DESIGNER, PORT OF AMSTERDAMPHOTO: R. OKAFOR

I like the unglamorous parts of product design: the empty states, the error messages, the admin tool nobody demos.

Most "design problems" are clarity problems wearing a costume. My job is to take a room full of half-formed worries and leave behind an interface so obvious it looks like it was always there.

Before Tide I designed at Stripe, consulted at IDEO's Cambridge studio, and helped a scrappy logistics startup ship weekly — the year I learned that taste without velocity is just opinion. I sketch in notebooks, prototype in code, and hold strong (negotiable) feelings about semicolons.
