A command-line tool for slow queries

The slow query is in there somewhere. Tern dives for it.

Tern reads the statistics your database already keeps, ranks every query by the time it costs you, and tells you what to change. No agent to deploy, no dashboard to check, no account to create.

How it works

Three commands between “it feels slow” and a fix.

Tern doesn't sit in your request path or proxy your traffic. It asks the database what it has been doing, then does the arithmetic you would otherwise do by hand in a psql session at 2 a.m.

1

Point it at a database

Pass a connection string. Tern reads pg_stat_statements or performance_schema with a read-only role.

tern watch $DATABASE_URL
2

See what costs the most

Queries are normalised, grouped, and ranked by total time consumed, so one 2-second query doesn't hide behind twenty thousand fast ones, or the reverse.

tern top --by total-time
3

Get the change to make

Tern reads the plan, names the cause in plain words, and proposes an index or rewrite with an estimated result.

tern explain 1

tern explain

A query plan, translated.

EXPLAIN output tells you everything and suggests nothing. Tern condenses it to four lines you can paste into a pull request.

plan
What the database is doing now, without the tree.
cause
The single reason this plan is expensive.
fix
DDL or a rewrite, safe to run on a live table.
est.
Projected timing, tested against a hypothetical index. Nothing is created.
~/shop — tern
$ tern explain 1
SELECT * FROM orders WHERE customer_id = $1
ORDER BY created_at DESC LIMIT 20
plan Seq Scan on orders (2,104,331 rows) → Sort
cause no index covers (customer_id, created_at)
fix CREATE INDEX CONCURRENTLY idx_orders_customer_created
ON orders (customer_id, created_at DESC);
est. 2.41s → 3ms hypothetical index via hypopg
write cost: +1 index on a table taking ~40 inserts/s. Acceptable.

What it catches

Built for the problems that make it to production.

01

Ranked by real cost

Sort by total time, p95, p99, rows scanned, or temp-file spill. The default is share of database time, because that's what your users feel.

02

N+1 detection

Tern spots identical statements fired in bursts and, if you use sqlcommenter tags, traces them back to the controller or job that sent them.

03

Index advice with a price

Every suggested index comes with its estimated write overhead and disk size. Tern also lists indexes nothing has used in 30 days.

04

Plan regressions

tern diff compares two snapshots and shows which queries changed plan, got slower, or appeared for the first time after a deploy.

05

Safe on production

Read-only connection, a statement timeout on its own queries, and no EXPLAIN ANALYZE unless you pass --analyze. Literals are redacted before anything is printed.

06

Plays well with pipes

--format json, csv, or markdown. Send it to jq, a Slack webhook, or a PR comment. Exit codes mean what you'd expect.

tern ci

Catch it in the pull request, not the postmortem.

Run your test suite under Tern and set a budget. If a change introduces a sequential scan on a large table or pushes a query past its limit, the build fails with the query and the line that issued it.

  • Fails on new queries over budget: --budget p95=200ms
  • Flags N+1 patterns introduced by the diff
  • Posts a summary as a PR comment with --format markdown
# .github/workflows/test.yml
- name: Run tests under Tern
  run: |
    tern ci \
      --db "$DATABASE_URL" \
      --budget p95=200ms \
      --fail-on seq-scan,n+1 \
      -- bin/rails test

# ✗ 1 query over budget
#   412ms  SELECT * FROM invoices WHERE status = $1
#          app/models/invoice.rb:88
#   exit 1

Install

One binary. On your machine in under a minute.

Tern ships as a single static binary for macOS, Linux, and Windows. It has no runtime dependencies and sends no telemetry.

brew install tern
curl -fsSL https://tern.sh/install | sh
cargo install tern-cli
docker run --rm ghcr.io/tern-sh/tern watch "$DATABASE_URL"

Then run tern doctor to check that your database has statement statistics enabled. If it doesn't, Tern prints the two lines of config you need.

Arctic terns fly 70,000 km a year. Your queries shouldn't.
